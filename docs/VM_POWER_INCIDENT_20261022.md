# 虚拟机挂起排查与修复边界

2026-10-22；现状尚未宣布修复完成。

## 证据

- 北京时间15:06:07与19:07:16，VMware日志记录vcpu上的 `PIIX4: PM Suspending... (to S1 (0x4))`，随后 `SUSPEND: Completed suspend` 成功完成。
- 是电源管理挂起流程，不是这些日志证明的崩溃；不能仅凭S1日志判断是空闲计时、用户点击还是宿主转发事件。
- 检查时宿主平衡电源方案：接电STANDBYIDLE=0（从不），电池STANDBYIDLE=600秒；保持电池保护，不修改宿主设置。
- 宿主在18:55—19:15查询42/107/506/507事件无返回；这是未取得证据，不等于宿主绝无电源事件。
- 当前VM处于挂起，vmrun列出0个运行VM。加密VM的Tools查询需要密码；不索取、猜测或在命令行保存加密密码。

## 最小修复

`deploy/desktop-vm/Fix-Guest-Power.cmd`由用户手动在guest执行。先核对WMI Manufacturer及Model均包含VMware；在宿主运行直接拒绝。只将guest当前电源方案的接电/电池空闲睡眠与休眠计时改为0，并打印前后值。没有自动登录、关闭锁屏、削弱安全防护、永久提权、计划任务或后台弹窗守护。

这是防止guest空闲睡眠的针对性修改，不防止用户主动挂起、关闭VMware时选择挂起、宿主断电/睡眠、guest更新重启或评估授权到期。

当前没有guest控制或文件传输通道，未执行脚本，也没有改VMX。官方 `suspend.disabled` 文档要求先关闭guest，当前为带内存状态的挂起且加密；不热改配置或删除.vmss来丢弃会话。

## 验收

1. 用户恢复VM并登录，将脚本放入guest后运行，检查四个电源计时结果为0。
2. 保留锁屏，不通过关闭认证维持无人值守。锁屏仍需交易门禁正确阻断，不能把“进程存活”当成可操作桌面。
3. 至少跨过前述空闲周期观察guest是否仍正常运行，再验证宿主最小化与VM控制台关闭行为。
4. 若再次挂起，读取guest System电源事件并与宿主/VMware事件按时间关联；不以脚本执行成功替代故障消失的证据。
5. 以后补齐独立健康监测与未知委托对账。不得靠自动重复下单来补偿会话异常。
